# Development architecture and verification

This is an implementation record, separate from the accepted [PRD](prd.md) and [experiment design](experiment-design.md). Development choices below are provisional apparatus adapters, not additions to the participant protocol. No participant data, headset verification, or Windows performance results are claimed.

## Installed toolchain and project structure

The available Mac has Unity **6000.0.48f1**, bundled Mono **6.13.0**, a working Roslyn C# compiler, and .NET runtime **6.0.21** without a .NET SDK. No tools or SDKs were installed and Unity licensing was not changed. `scripts/test.py` discovers an existing Unity installation; `STROOP_UNITY_CONTENTS` may point to another installed `Unity.app/Contents`. An existing .NET 8 SDK can also run `dotnet run --project AvatarStroop.Regression.csproj`.

The portable C# core lives in `Assets/Stroop/Core`, so the same source can be compiled in Unity and the independent regression executable. The core has no dependency on Unity frame timing, XR, a headset SDK, or external packages. Presentation adapters must acknowledge actual stimulus presentation with the current trial ID; generating a planned trial alone does not start RT. Production apparatus timing requires measurement of the eventual adapter's timestamp semantics and uncertainty.

Adapter boundaries are: participant application owns the task and first-response input; independent operator application captures its own head/eye stream; a shared avatar presentation interface accepts either the automatic source or the locked operator source; participant gaze remains a separate measurement stream. Simulated transport must be visibly labelled and stored in simulation sessions. A simulator is not real WoZ. There is no automatic fallback between sources.

## Milestone 1: deterministic task core

Implemented: constrained 24-trial lists, four Williams orders, independent B initial-target balancing, varying list assignment, practice with correction/Continue and at most two attempts, owner-only block configuration, presentation acknowledgement, press-edge input, fixed questionnaire wording, separate ratings, additional 30-second minimum rest including after the fourth block, explicit pause/resume, and structured in-memory events.

All four main lists use the same multiset and are distinct. Planning uses a versioned deterministic PRNG; list IDs encode algorithm/index/derived seed and the session records the original seed. Allocation IDs include algorithm version, roster count, seed, and slot. Freeze the generated roster before use: generating a different roster size is a different schedule, not an extension of the old one. The planner accepts no performance inputs and does not reassign after withdrawal.

The owner's role is an application-boundary capability, without a new account system. This core checks the role on configuration methods; the participant interface must not expose owner commands. The accepted assigned condition/order/B target cannot be overridden through block configuration. Configuration records the chosen source and requires an adapter readiness result before countdown; resumption during main task or its countdown also requires reacquisition. Real readiness is not implemented by a test boolean.

The engine hides task/avatar during explicit pause, freezes active time, flags an interrupted trial without correctness or RT, and resumes the next planned trial in a new segment after the same configured countdown. A pause on the final planned main trial resumes into ratings without adding a trial. The development source keeps acquiring during pause to reacquire the selected block/segment; paused observations are diagnostic rather than active exposure.

## Milestone 1 boundaries and continuing open decisions

- Countdown duration and questionnaire language have no hidden study defaults. A caller must provide both; tests use **1 second** and English strictly as engineering fixtures. Confirm the participant protocol before use.
- Practice interruption scoring is not specified in the baseline. An interrupted scored-practice trial remains interrupted; resumption enters `NeedsProtocolDecision` instead of inventing a denominator, incorrect response, replacement, or extra attempt. Withdrawal and technical termination remain available. Ordinary main-task pause/resume is implemented.
- `FlagTechnicalIssue` marks an audit issue without selecting an automatic pause/recovery policy. Detection thresholds, notification side/content, automatic suspension, and recovery decisions remain unresolved. Production use must remain gated until these are frozen and validated.
- Non-main operator views currently expose no task/performance detail. Main operator view has the same current trial ID/stimulus and a participant-avatar visibility request; avatar appearance/drive remain unresolved. The operator-side D and non-main views are explicitly marked `OperatorViewProvisional`; the D visibility request is a development placeholder, not an accepted display decision. No reverse participant eye, body, hand, or voice synchronization is implied.
- This milestone contains view models and in-memory audit data, not a Unity scene, persistent export, real tracking, or two-computer transport. Subsequent milestones implement and test those adapters separately.
- No research endpoint, sample size, RT exclusion rule, significance criterion, fault timing threshold, or calibration pass criterion is introduced.

## Milestone 2: control, transport, clocks and fault facts

Software version `0.2.0-dev` adds a shared `AvatarController`, the exact automatic 3.0/.5/3.0/.5-second reference with smooth head/eye interpolation, separate raw and effective head/eye validity, an explicitly unavailable real-operator adapter, and a deterministic continuous simulator whose head and eyes do not follow the automatic trajectory. A locked controller rejects different origins, streams, sessions, blocks, segments and participant measurements. Missing live input produces no current pose and never uses the automatic reference as actual output. `RenderValidated` also applies per-axis transport usability without rewriting the raw sample or promoting invalid tracking to valid.

`Transport.cs` implements a provisional versioned UDP grammar, not the frozen lab protocol. Packet identities and source sample identities are separate. Incoming data is bounded, parsed with invariant numeric/identity rules, pinned to the expected endpoint and peer/session/role/source/device/clock, and rejected on malformed, duplicate, out-of-order, stale or impossible time values. Task snapshots contain phase, trial identity and stimulus, with no response, correctness, RT or ratings. This transport currently allows operator-control tracking only; no reverse participant-gaze synchronization is implied. Remote networking requires explicit opt-in and an agreed development network; the packet grammar is not an authentication mechanism.

Clock exchanges correlate four monotonic timestamps. The provisional estimator exposes offset, drift availability, feasible rate bounds, uncertainty, named clock mapping and a bounded extrapolation horizon. Uncertainty includes the feasible affine rate interval and expands with extrapolation; unbounded rate prevents extrapolation. Tests include synthetic clock offsets/drift and changing asymmetric transit that can otherwise masquerade as drift and make stale data appear current. These are computed development estimates, not validated physical timing accuracy. No packet is current-render-usable without a matching clock map and bounded capture age. Local receipt freshness and raw tracking validity remain separate diagnostic facts.

The receive monitor distinguishes head invalidity, eye invalidity, stale input, missing mapping and stale connection. A connection gap latches `RecoveryDecisionRequired`; later hello packets or new samples remain diagnostic and cannot revive old or new rendering automatically. A new agreed recovery procedure is still required. This is development transport gating, not an approved participant automatic-pause or recovery policy. **The current engine refuses all `RunKind.Apparatus` sessions** until real acquisition/mapping, fault/recovery rules, calibration and timing validation are completed.

M2 does not claim rendered VR faults, two independent app processes, persistent export or headset acquisition; these are separate integration checks. M2 actual verification: **60 test groups passed, 0 failed**, including a real temporary UDP loopback exchange and rejection of an unexpected source endpoint. Local socket tests require sandbox permission; the authorized regression was run with that permission. The core and tests compile with warnings as errors.

The added [regression workflow](../.github/workflows/regression.yml) requests Linux and Windows .NET 8 runs with read-only repository permissions and no deployment. Action major versions were checked against the official [checkout](https://github.com/actions/checkout) and [setup-dotnet](https://github.com/actions/setup-dotnet) repositories. The M2 workflow actually succeeded on both `ubuntu-latest` and `windows-latest` at exact commit `267715c597503a08f80215b8b1943f2412ad5d31`: [run 40715956883](https://github.com/MingyuanZhu7719/avatar-gaze-stroop-demo/actions/runs/40715956883). Those hosted runner results validate the portable .NET tests, not the lab Windows computers or headsets.

## Milestone 3: integrated simulation applications and auditable export

Software `0.3.0-dev` adds two independently launched app roles sharing the portable engine, typed owner commands, participant-side state/input, operator-side independent continuous head/eye simulation, task snapshots, separate clock mappings and the common avatar output. The runnable console host is `AvatarStroop.Simulator.csproj`; the Unity bootstrap uses the same runtime applications. The development wire grammar is version 2, adding operator-only safety-stop requests and participant acknowledgements. The participant owns pause; stop retries use one request identity and are idempotent even after local resume. The operator sees pending versus acknowledged delivery and has no remote resume or configuration command. This development UDP path does not establish a production emergency-stop guarantee.

The source context is broadcast in block preparation, countdown and pause so the operator can produce the required new block/segment before readiness is satisfied. Resuming waits for a fresh selected-source context, never a cached old pose. The next block resets its segment before configuration/readiness. Runtime regression exercises pause, next-trial resume, final-response transition, five ratings, the actual 30-second minimum rest, and a usable simulator source in the next block.

[Unity adapter source](unity-adapter.md) constructs world-space task, rating/rest, avatar and fault objects. Participant/target directions are derived from the actual development scene; ray tests verify A/C alignment. Per-axis invalid tracking is held visibly only as a labelled renderer policy and remains invalid in audit fields. Input changes are followed by a new presentation snapshot before rendering. Camera observations capture their own phase/block/segment/trial, output, requested visibility, applied pose and held-axis flags, avoiding stale pre-input audit context. The camera callback is a render proxy, not measured photon onset. A fixed participant-avatar placeholder in the operator view does not implement participant eye/head synchronization.

The [separate owner console](owner-console.md) is enabled only by an explicit local command-file launch path. It can start practice, lock the assigned block's automatic or simulator source, begin after readiness, and export through a fixed host callback. It cannot alter allocated factors or resume remotely. Live selection is rejected before locking because its adapter is unavailable. The file interface has session binding, exclusive execution, durable intent/receipts and duplicate/uncertain-outcome handling; it is a trusted local development boundary rather than production authentication. No owner selector is added to the participant view. Existing Editor context commands remain useful during development.

[CSV data bundles](data-schema.md) preserve configuration and trial-list seed, trial/event/rating linkage, raw accepted operator samples, mapped controller output separately from renderer-applied pose, independent participant gaze/AOI contracts, clock/transport evidence, fault flags and software/build identity. Every exported table has a final SHA-256 manifest entry. Partial session export is supported and never marked as completed research. The audit is accumulated in memory and exported as a snapshot; continuous crash-resilient session streaming remains unfinished. The simulator also writes its own raw acquisition TSV separately from receiver acceptance. Real participant gaze is unavailable and remains missing rather than being copied from operator control.

Clock audit uses a monotonic mapping revision, including invalidation, rather than the retained observation count. A regression exports 80 successive exchanges plus same-count invalidation past the 64-observation window. The actual reference time, offset, drift, estimated uncertainty, feasible rate bounds and named clocks remain reconstructable. The v2 estimate selects a feasible interval midpoint when an unconstrained fit falls outside that interval, instead of clipping onto its extreme. A deterministic three-exchange regression reproduces the former one-machine-step intercept inversion despite a physically feasible clock; the correction keeps the full feasible-rate uncertainty and unchanged capture-age checks. New clock replies are evaluated together with the retained causal constraints before they replace any observation. This prevents an old biased point estimate from repeatedly rejecting physically valid replies. The existing round-trip quality limit is checked against the worst transit across the full causal rate interval; an ambiguous or excessive result is rejected without changing the prior window. The quality limit does not narrow the physical uncertainty interval or imply a study timing criterion. An incompatible candidate interval is rejected; the prior mapping remains unchanged. These are software estimates with known development assumptions, not verified physical synchronization.

The headless app now also retains at most 256 correlated reply diagnostics per role in `participant-clock-exchanges.tsv` and `operator-clock-exchanges.tsv`. They contain exact round-trip-serialized four timestamps, acceptance/rejection, mapping revision/availability/reason, feasible rates and point-estimate method. The final report includes the map failure reason, and the integration script prints its evidence directory before assertions and bounded raw clock evidence on verification failure. The initial failed integration evidence did not contain operator exchange timestamps, so its exact failed branch cannot be retrospectively proven; the numerical defect was independently reproduced and regression-tested before publication. The separate persistent-reply lockout was reproduced with 30 valid replies and is also a committed regression. An additional local investigation stress run covered 100,000 synthetic datasets (asymmetric transit, narrow transit, long clock uptime and exact zero-transit cases): all were admitted with available maps, and 499,712 successful mapped-time checks contained their known true affine time. This supports software behavior within those fixtures, not hardware timing accuracy.

### Editor attempt and remaining apparatus work

One ordinary installed Editor batch run was attempted with `-batchmode -nographics -noUpm -quit` and the scene-builder entry point. It exited **1 before import/scene generation** because **no valid Unity Editor license was found**. No activation, credentials, license change, package install or retry was performed. This was a missing licensing prerequisite, not an automatic approval rejection. Full logs remain local and are not published.

Consequently the generated scenes, shader compilation, actual camera-render behavior, Unity standalone player builds and rendered owner-command workflow have not been executed. The existing source and managed compile are reviewable, and the separate console applications are executable; these do not amount to a completed dual-VR apparatus. Real VIVE Pro Eye acquisition/SDK integration, participant gaze capture, calibration/coordinate mapping, two physical computers, controller mapping, measured display/network timing, and headset tests remain unavailable here. The fault policy and its thresholds/recovery, countdown/language and other accepted TBD decisions must be frozen by the study owner before apparatus admission is implemented. `RunKind.Apparatus` stays blocked.
